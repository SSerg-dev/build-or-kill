## 1. System Classification

**System Type:** Structured advisory generation

**Description:**
Build or Kill uses an LLM to turn a founder's SaaS idea into a structured advisory result. The user provides a product description, target audience, and main pain/problem. The system either asks 2-3 clarification questions for weak input or returns a concise BUILD / PIVOT / KILL recommendation with confidence score, five role-based analyses, risks, MVP scope, validation experiments, and next actions. Good output is specific, actionable, concise, advisory, and based only on the user-provided input.

**Critical Failure Modes:**
1. Producing a final verdict for extremely weak input instead of asking clarification questions.
2. Inventing market data, competitor research, or external validation that was not provided.
3. Returning malformed or incomplete structured output.
4. Presenting the verdict as a guarantee of business success.
5. Producing generic startup advice that does not reference the user's actual idea, audience, and pain/problem.

## 1b. Domain Context

**Industry Vertical:** Startup idea validation / developer tooling

**User Population:** Solo developers, indie hackers, and technical founders evaluating SaaS ideas before building.

**Stakes Level:** Medium

**Output Consequence:** The user may decide whether to build, pivot, or kill an idea. The output should reduce wasted development time, but must not replace real customer validation.

### What Domain Experts Evaluate Against

| Dimension | Good | Bad | Stakes | Source |
|-----------|------|-----|--------|--------|
| Problem clarity | Names a concrete pain and why it matters to a specific audience | Treats a vague product category as a validated problem | High | `docs/specs/SPEC.md` |
| Audience specificity | Identifies a narrow, reachable target user | Uses broad labels like "everyone", "businesses", or "creators" without focus | High | `docs/specs/SPEC.md` |
| MVP realism | Recommends a small testable scope | Encourages a broad platform, dashboard, CRM, or multi-feature build | High | `docs/specs/SPEC.md` |
| Validation quality | Suggests concrete experiments the founder can run quickly | Gives generic "talk to users" advice without a test shape | High | `docs/specs/SPEC.md` |
| Advisory restraint | States uncertainty and avoids fabricated evidence | Implies real market research, competitor analysis, or guaranteed success | Critical | `docs/specs/SPEC.md` |

### Known Failure Modes in This Domain

1. False confidence: the model sounds certain despite thin input.
2. Idea inflation: the model expands the MVP into a business plan or platform.
3. Fake evidence: the model invents market size, competitor claims, or user demand.
4. Generic validation advice: experiments are too vague to run.
5. Role collapse: the five advisory roles repeat the same points instead of adding distinct perspectives.

### Regulatory / Compliance Context

No regulated financial, legal, or medical advice is in scope. The system still needs a clear advisory disclaimer because users may make business decisions from the output.

### Domain Expert Roles for Evaluation

| Role | Responsibility |
|------|---------------|
| Experienced indie founder | Review whether recommendations are practical and MVP-first |
| Product strategist | Calibrate problem/audience/MVP realism rubrics |
| Growth/operator reviewer | Calibrate validation experiment quality |
| Technical founder | Review technical feasibility and build-scope realism |

## 2. Framework Decision

**Selected Framework:** OpenAI Responses API with Structured Outputs JSON schema

**Version:** Responses API, using `text.format` JSON schema support. Pin the OpenAI SDK package version during implementation.

**Rationale:**
The MVP needs one structured advisory generation flow, not a durable multi-agent runtime. The five expert roles can be represented inside one schema-constrained response, keeping latency, implementation complexity, and evaluation scope low. Official OpenAI docs describe the Responses API as the primary interface for model responses and Structured Outputs as the preferred way to ensure schema adherence.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| OpenAI Agents SDK | Useful for true handoffs or tool-using agents, but unnecessary overhead for one structured advisory response |
| LangGraph | Strong for durable stateful workflows, but too heavy for this MVP |
| CrewAI | Role abstraction maps to the advisory-board metaphor, but adds multi-agent orchestration without clear MVP value |
| JSON mode only | Ensures valid JSON but does not guarantee schema adherence; Structured Outputs is preferred |

**Vendor Lock-In Accepted:** Partial. The MVP accepts OpenAI lock-in for speed and structured output reliability. Keep the AI call isolated behind an internal adapter so a future provider swap is possible.

```ts
      name: "build_or_kill_result",
      strict: true,

```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| Responses API | OpenAI response-generation endpoint | Main advisory and clarification calls |
| Structured Outputs | JSON schema-constrained model output | Final result and clarification-question payloads |
| Refusal handling | Programmatic detection of safety refusals | Error/fallback handling when model refuses |
| Adapter boundary | Local wrapper around OpenAI calls | Keep UI independent from provider details |

### Common Pitfalls
1. Using JSON mode instead of Structured Outputs and then discovering the payload is valid JSON but wrong shape.
2. Asking for market data or competitor research despite the SPEC forbidding fabricated research.
3. Mixing clarification output and final verdict output in one loose schema without an explicit mode/type.
4. Letting the five roles become five separate network calls before the MVP proves it needs that complexity.

## 4. Implementation Guidance

**Model Configuration:**
Use a Responses-compatible OpenAI model that supports Structured Outputs. Default via `OPENAI_MODEL`; pin a production model after implementation evals. Use low randomness for consistency; start with `temperature` unset or low if supported by the selected model. Keep max output bounded by concise result requirements.

**Core Pattern:**
Use a two-output-mode adapter:
1. `clarification_needed` result with 2-3 questions and no verdict.
2. `final_result` with exactly one verdict and all required result sections.

The app validates required fields before the AI call. The AI determines weak/generic/ambiguous input and returns clarification questions instead of a verdict when needed.

**Tool Use:**
No web search, scraping, file search, or competitor research tools in MVP. The model must reason only from the provided user input and clarification answers.

**State Management:**
Persist only local UI state and old/last result in `localStorage`. Do not create accounts, server-side history, dashboards, or analytics.

**Context Window Strategy:**
Keep prompts compact. Send only validated idea fields, optional notes, and clarification answers. Do not include previous unrelated analyses.

## 4b. AI Systems Best Practices

### Structured Outputs with Pydantic

Use a schema equivalent to this model. TypeScript/Zod may be used in implementation, but this Pydantic shape defines the contract clearly for evals and validation.

```python
from typing import Literal
from pydantic import BaseModel, Field

class RoleAnalysis(BaseModel):
    role: Literal[
        "Product Strategist",
        "CTO",
        "Growth Marketer",
        "Skeptic",
        "Investor / Business Reviewer",
    ]
    focus: str
    bullets: list[str] = Field(min_length=2, max_length=4)

class ClarificationResult(BaseModel):
    result_type: Literal["clarification_needed"]
    questions: list[str] = Field(min_length=2, max_length=3)
    reason: str

class FinalResult(BaseModel):
    result_type: Literal["final_result"]
    verdict: Literal["BUILD", "PIVOT", "KILL"]
    confidence_score: int = Field(ge=0, le=100)
    verdict_reason: str
    role_analyses: list[RoleAnalysis] = Field(min_length=5, max_length=5)
    key_strengths: list[str]
    key_risks: list[str]
    mvp_scope: list[str]
    validation_experiments: list[str]
    recommended_next_actions: list[str]
    advisory_disclaimer: str
```

### Async-First Design

Run AI calls asynchronously with explicit loading and error states. Do not block the one-page UI. Streaming is optional; for MVP, non-streamed structured output is simpler because the UI needs a complete valid object before rendering.

### Prompt Engineering Discipline

Separate system and user content. The system prompt defines roles, restrictions, output rules, and advisory limitations. The user payload is structured JSON containing the idea fields. Do not rely on prompt wording alone for structure; schema validation is mandatory.

### Context Window Management

Do not accumulate prior submissions in the AI context. If using `localStorage`, display the stale result locally but do not send it into the next AI call unless explicitly needed for a future comparison feature, which is out of MVP scope.

### Cost and Latency Budget

Use one model call for initial analysis. If clarification is needed, use one additional final-analysis call after answers are complete. Mock/demo mode must bypass live API calls. Target the SPEC's 2-3 minute user workflow; latency should feel responsive, with visible loading state.

## 5. Evaluation Strategy

### Dimensions

| Dimension | Rubric (Pass/Fail or 1-5) | Measurement Approach | Priority |
|-----------|--------------------------|---------------------|----------|
| Schema validity | Pass if output validates against the selected schema with no missing required fields | Code | Critical |
| Clarification routing | Pass if weak input returns 2-3 questions and no verdict; strong input returns final result | Code + Human | Critical |
| Verdict exclusivity | Pass if final result has exactly one of BUILD, PIVOT, KILL | Code | Critical |
| Grounding in provided input | 1-5 score; 5 references concrete user-provided problem/audience/pain, 1 invents unsupported context | LLM Judge calibrated by human review | Critical |
| Non-fabrication | Pass if no market size, competitor claims, or real research claims are invented | LLM Judge + Human sampling | Critical |
| Actionability | 1-5 score; 5 gives concrete MVP scope, validation experiments, and next actions a founder can run | Human + LLM Judge | High |
| Role differentiation | 1-5 score; 5 means each role contributes distinct perspective without repetition | Human sampling | Medium |
| Concision | Pass if sections are bullet-oriented and avoid business-plan prose | Code + Human | Medium |

### Eval Tooling

**Primary Tool:** Promptfoo for prompt/schema regression tests; optional Arize Phoenix for tracing once live calls exist.

**Setup:**
```bash
npm install -D promptfoo
```

**CI/CD Integration:**
```bash
npx promptfoo eval
```

### Reference Dataset

**Size:** Start with 15 examples.

**Composition:**
- 5 strong inputs that should produce final verdicts.
- 4 weak/generic inputs that should trigger clarification.
- 3 unrealistic-scope inputs that should lean PIVOT or KILL.
- 2 ambiguous-audience inputs that should trigger clarification.
- 1 adversarial input asking for market/competitor claims.

**Labeling:**
Initial labels can be authored by the developer against the SPEC. Before real launch, calibrate at least 5 examples with an experienced founder/product reviewer.

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Required field validation | Missing product description, target audience, or main pain/problem | Block submit and show inline validation |
| Empty clarification answer | Any generated clarification question has no answer | Block final analysis and show inline validation |
| Schema validation failure | OpenAI response cannot be parsed into expected schema | Retry once or fall back to demo/mock error state |
| Forbidden research claim | Output claims market data, competitor research, or guaranteed success | Block result and show safe error/fallback |
| Unsupported result state | Final output has multiple/no verdicts or invalid confidence score | Block result and retry/fallback |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Clarification precision | Sample weak and strong submissions from eval set | Adjust weak-input rubric and prompt |
| Generic-output rate | Review low-specificity outputs | Tighten prompt and add examples |
| Fabrication rate | Review outputs flagged for unsupported claims | Add guardrail tests and stricter refusal instructions |
| Actionability score | Periodic human review of validation experiments and next actions | Refine rubric and prompt examples |

## 7. Production Monitoring

**Tracing Tool:** Arize Phoenix once live API calls exist; local logging is acceptable during early MVP/demo mode.

**Key Metrics to Track:**
- Schema validation pass rate.
- Clarification-needed rate.
- API latency and failure rate.
- Mock fallback activation count.
- Eval pass rate for reference dataset.

**Alert Thresholds:**
- Schema validation failures above 2% of live calls.
- API error rate above 5% over a demo/test session.
- Any detected forbidden research claim in sampled output.
- Eval suite below 90% pass before release.

**Smart Sampling Strategy:**
Prioritize samples where input is very short, target audience is broad, output confidence is high, verdict is BUILD, or guardrails/retries were triggered.
